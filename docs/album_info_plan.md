# 앨범·아티스트 정보 가져오기 계획서 (eztag 메타데이터 소스 활용)

- **작성일:** 2026-10-31
- **대상 버전:** 0.11 이후
- **상태:** 계획 (구현 전)
- **참고 소스:** `zardkim/eztag` `backend/app/core/metadata/` (커밋 `f5423d3`, 2026-09-19)

## 1. 목표

앨범 화면에 앨범 소개, 발매일, 발매사, 장르, 앨범 종류(정규·EP·싱글·OST)를 보여 준다. 아티스트 화면에는 아티스트 소개를 보여 준다. 정보는 멜론·벅스·애플 뮤직에서 가져오되, eztag에 이미 만들어 둔 검색·파싱 코드를 재사용한다.

음악 파일의 태그는 바꾸지 않는다. 태그 편집은 eztag가 맡고, muzplayer는 가져온 정보를 자기 DB에만 저장해서 보여 준다.

## 2. eztag 소스 분석 결과

| 모듈 | 방식 | 인증 | 가져오는 항목 | 재사용 |
|---|---|---|---|---|
| `melon.py` | 검색·앨범 상세 HTML 파싱 | 없음 | 앨범명, 아티스트, **앨범 소개**, 발매일, 장르, 발매사·기획사, 앨범 종류([EP]·[싱글]·[정규]·[OST]), 고해상도 커버, 트랙 목록 | **1순위** |
| `bugs.py` | 검색·앨범 상세 HTML 파싱 | 없음 | 앨범명, 아티스트, 발매일, 장르, 발매사, 앨범 종류, 커버, 트랙 목록 (소개 없음) | 보조 |
| `apple_music.py` | 페이지 안의 JSON 파싱 | 없음 | 앨범명, 아티스트, 발매일, 장르, 발매사, 커버, 트랙 목록 (소개 없음) | 보조 (해외 음반) |
| `apple_music_classical.py` | 위와 같음 | 없음 | 클래식 전용 필드 (작품·악장·작곡가) | 제외 |
| `spotify.py` | 공식 API (spotipy) | Client ID·Secret | 앨범 종류 (album/single/compilation), 발매일 | 제외: 키가 필요하고 한국 음반 정보가 적음 |
| `matcher.py` | 검색어 정규화, 유사도 점수 | — | 전각→반각, feat 제거, 괄호 제거, 제목·아티스트·길이 점수 | **그대로 사용** |
| `bugs_lyrics.py`, `alsong.py`, `lrclib.py` | 가사 검색 | 일부 비공식 | 싱크 가사(LRC) | 이번 범위 밖 (8절) |

확인한 사실:

- **앨범 소개는 멜론만 준다.** `_parse_album_info()`가 `div#d_video_summary` 또는 `div.dtl_albuminfo`를 읽는다.
- **아티스트 소개를 가져오는 코드는 eztag에 없다.** 아티스트 소개(데뷔, 소속사, 멤버, 소개글)는 멜론 아티스트 상세 페이지(`/artist/detail.htm?artistId=`) 파서를 새로 써야 한다.
- **eztag는 앨범 종류를 파일 태그에 쓰지 않는다.** `tag_writer.py`에는 `RELEASETYPE`이나 `TCMP`가 없다. 그래서 eztag로 태그한 파일은 0.11의 태그 기준만으로는 비정규·컴필레이션이 잘 나뉘지 않을 수 있다. 사이트의 앨범 종류가 이 빈틈을 메운다 (6절).
- **`bugs_lyrics.py`에는 벅스 API 키가 소스에 그대로 들어 있다.** 이 파일은 가져오지 않는다.

## 3. 코드를 가져오는 방식

- eztag는 별도 이미지라서 패키지로 공유할 수 없다. 필요한 파일만 `backend/app/metadata/`로 **복사**하고, 파일 머리에 출처(저장소, 커밋)를 적는다.
  - 대상: `melon.py`, `bugs.py`, `apple_music.py`, `matcher.py`
  - 바꿀 것: 로깅 형식, 타임아웃, User-Agent, 요청 간격(전역 제한기), muzplayer 예외로 통일
- 의존성 `requests`, `beautifulsoup4`가 늘어난다. 이미지는 1~2MB 커진다.
  - 대안: 지금처럼 `urllib`로 바꿔 쓰면 의존성은 안 늘지만, 원본과 차이가 커져 eztag 쪽 수정 사항을 따라가기 어렵다. **복사 후 최소 수정**을 권한다.
- 사이트 구조가 바뀌면 eztag와 muzplayer를 둘 다 고쳐야 한다. 파서를 고칠 때 두 저장소에 같은 커밋을 넣는 것을 규칙으로 한다.

## 4. 데이터 모델 (마이그레이션 0009)

`album_info` 테이블 — 앨범당 한 줄:

| 열 | 내용 |
|---|---|
| `album_id` (PK, FK) | 앨범 |
| `status` | `matched` · `candidates` · `not_found` · `manual` · `error` |
| `provider`, `provider_id`, `url` | 어디서 가져왔는지 (melon/bugs/apple) |
| `description` | 앨범 소개 (멜론) |
| `release_date`, `label`, `genre` | 발매일, 발매사, 장르 |
| `release_type` | `album` · `ep` · `single` · `soundtrack` · `compilation` |
| `score` | 자동 매칭 점수 |
| `candidates` (JSON) | 점수가 모자랄 때 고를 후보 (최대 5개) |
| `checked_at` | 마지막 확인 시각 (다시 확인 주기 계산용) |

`artist_info` 테이블 (3단계): `artist_id`, `provider_id`, `url`, `description`, `debut`, `agency`, `members`, `checked_at`.

음악 파일이 지워져 앨범이 정리되면 `ON DELETE CASCADE`로 같이 지운다. 앨범을 다시 만들어도 앨범 id가 유지되는 경우(재스캔)에는 정보가 남는다.

## 5. 매칭과 실행

**검색어:** 앨범 아티스트 + 앨범명. `normalize_search_query()`로 특수문자와 괄호를 정리한다. 앨범명의 `[2019]`, `(Remastered)` 같은 꼬리는 떼고 한 번 더 찾는다.

**점수:** `matcher.py`의 유사도에 두 가지를 더한다.
- 수록곡 수가 같은지
- 발매 연도가 같은지 (태그에 연도가 있을 때)

**결정:**
- 점수 85 이상이면 자동으로 연결한다 (`matched`).
- 50~85이면 후보로 저장하고, 앨범 화면에 "이 앨범이 맞나요?" 선택지를 띄운다 (`candidates`).
- 그 아래면 `not_found`로 둔다. 멜론 앨범 주소를 붙여 넣어 직접 연결할 수도 있다 (`manual`).

**실행:**
- **요청 처리 중에는 외부 사이트를 부르지 않는다.** 0.9.1·0.10.0의 DB 연결 고갈과 같은 종류의 문제를 피하기 위해서다. 아티스트 사진(`artist_images.py`)처럼 **백그라운드 작업 하나**로 돌린다.
- 관리자 화면에 "앨범 정보 가져오기" 버튼을 두고, 진행률(완료 / 전체 / 찾음)을 보여 준다.
- 앨범 화면의 "정보 찾기"는 그 앨범 하나를 작업 대기열 맨 앞에 넣는다.
- 사이트별 요청 간격은 최소 1.5초로 하고, 403·429 응답을 받으면 10분 쉰다. 같은 응답이 연속 3번 오면 작업을 멈추고 관리자 화면에 알린다.
- 다시 확인하는 주기는 `not_found` 30일, `matched` 180일이다. `manual`은 다시 확인하지 않는다.
- 앨범 8,000개 기준으로 처음 한 번 도는 데 약 3~4시간(요청 간격 1.5초 × 검색·상세 2회)이 걸린다. 스캔처럼 밤에 자동으로 돌리는 설정을 둔다.

**DB 연결:** 작업은 앨범 하나를 처리할 때만 세션을 열고 바로 닫는다. 네트워크 요청을 기다리는 동안에는 연결을 쥐지 않는다.

## 6. 앨범 종류(비정규·컴필레이션)와 연결

0.11은 폴더와 태그만으로 앨범 종류를 정한다. 사이트 정보가 생기면 우선순위는 다음과 같다.

1. 폴더 (관리자가 정한 컴필레이션 폴더, "비정규" 폴더)
2. 태그 (`TCMP`·`cpil`, `RELEASETYPE`, 앨범명의 "- Single" 등)
3. **사이트의 앨범 종류** (`ep`·`single` → 비정규, `compilation`·`soundtrack` → 컴필레이션)

앨범 종류는 지금 앨범을 구분하는 키 `(종류, 앨범 아티스트, 앨범명)`의 일부다. 사이트 정보로 종류가 바뀌면 곡을 새 앨범으로 옮겨야 하는데, 이 일은 다음 스캔이 한다. 스캔이 이미 하고 있는 "폴더 종류가 바뀌면 다시 분류" 경로를 그대로 쓴다. 별점·좋아요·영상은 지금처럼 새 앨범으로 따라간다.

## 7. 화면

**앨범 화면**
- 제목 아래에 발매일 · 발매사 · 장르 · 종류 배지(EP, 싱글, OST)를 둔다.
- 앨범 소개는 처음 4줄만 보여 주고 "더 보기"로 펼친다.
- 출처 링크(예: "멜론에서 보기")를 둔다.
- 후보 상태이면 후보 카드 3~5개(커버, 앨범명, 아티스트, 발매일)와 "이 앨범 맞음" / "모두 아님" 버튼을 보여 준다.
- 관리자에게는 "정보 다시 찾기"와 "주소로 연결"을 보여 준다.

**아티스트 화면 (3단계):** 사진 옆에 소개 2~3줄, 데뷔, 소속사, 멤버를 둔다.

**관리자 화면:** "앨범 정보" 카드에 가져오기 / 멈추기 버튼, 진행률, 사이트별 성공·실패 수, 마지막 오류를 둔다.

두 테마(기본·Plexamp 스타일) 모두에서 새 요소가 토큰 색만 쓰게 한다.

## 8. 범위 밖 (나중에 따로)

- **가사 가져오기:** 앱은 이미 태그와 `.lrc` 파일의 가사를 보여 준다. LRCLIB은 공개 API라 붙이기 쉽다. 벅스·알송은 비공식이거나 키가 하드코딩돼 있어 권하지 않는다.
- **태그에 다시 쓰기:** 이건 eztag의 일이다. muzplayer는 파일을 읽기만 한다 (음악 폴더는 읽기 전용 마운트를 권장).
- **커버 교체:** 사이트의 고해상도 커버로 바꾸는 기능. 원하면 2단계에 추가할 수 있다.

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 사이트 HTML 구조가 바뀌어 파서가 깨짐 | 사이트별로 실패를 집계한다. 실패해도 앱 나머지는 정상으로 동작하고, 저장된 정보는 지우지 않는다. 파서 테스트용 HTML 샘플을 저장소에 둔다. |
| 너무 자주 요청해 IP가 차단됨 | 요청 간격, 403·429 때 쉬기, 하루 최대 요청 수를 둔다. 기본값은 보수적으로 잡는다. |
| 이용약관·저작권 | 개인 서버에서 본인이 보는 용도로만, 낮은 빈도로 쓴다. 소개글은 화면에만 보여 주고 다른 곳으로 내보내지 않는다. 출처 링크를 함께 표시한다. |
| 잘못된 앨범에 연결됨 | 점수 기준을 높게 잡고, 애매하면 사람이 고르게 한다. 연결 해제 버튼을 둔다. |
| 이미지·의존성 증가 | `requests`, `beautifulsoup4`만 추가한다 (의존 패키지 포함 1~2MB). |

## 10. 단계

| 단계 | 내용 | 규모 |
|---|---|---|
| 1 | 멜론 앨범 정보: 복사·정리, `album_info` 테이블, 백그라운드 작업, 앨범 화면 표시, 관리자 카드 | 중 |
| 2 | 후보 고르기·주소로 연결, 벅스·애플 보조 검색(멜론에 없을 때) | 중 |
| 3 | 아티스트 소개: 멜론 아티스트 페이지 파서(새로 작성), `artist_info`, 아티스트 화면 | 중 |
| 4 | 사이트 앨범 종류를 비정규·컴필레이션 판정에 반영 (6절) | 소 |

## 11. 정해 주셔야 할 것

1. **사이트 우선순위:** 멜론 → 벅스 → 애플 순서로 괜찮은지.
2. **자동 연결 기준:** 점수가 높으면 자동으로 연결해도 되는지, 아니면 모두 직접 확인할지.
3. **아티스트 정보:** 소개글 외에 데뷔·소속사·멤버도 필요한지.
4. **실행 시점:** 관리자가 버튼을 누를 때만 돌릴지, 매일 밤 자동으로 돌릴지.
