# 검색 고도화 계획서

- 작성: 2026-11-08 (muzplayer 0.56.0 기준) · 1단계(아티스트 별칭)는 0.57.0에서 구현
- 목표: "머라이어 캐리"로 `Mariah Carey`가, "아이유"·"IU" 어느 쪽으로도 같은 가수가 찾아지게 한다. 이어서 오타, 표기 차이, 한/영 자판 실수까지 너그럽게 찾는다.

## 1. 지금의 검색 (search_index.py)

| 되는 것 | 안 되는 것 |
|---|---|
| 대소문자·전각·악센트·문장부호 무시 (`Don't` = `dont`) | **다른 언어 표기**: "머라이어 캐리" → `Mariah Carey` ✗ |
| 띄어쓰기 무시 ("밤편지" = "밤 편지") | **외래어 표기 흔들림**: "머라이어 케리" ✗ |
| 한글 초성 ("ㅇㅇㅇ" → 아이유) | **오타**: "머라이어 캐라" ✗ |
| 여러 단어는 순서 상관없이 모두 포함 | **한/영 자판 실수**: "dkdldb"(=아이유) ✗ |
| 곡은 제목·아티스트·앨범 어디에 있어도 | 결과 순서가 단순 (정확히 같은 이름이 앞에 오지 않을 때가 있음) |

검색은 곡·앨범·아티스트마다 미리 만든 `search_text`를 trigram 인덱스로 `LIKE` 검색한다. 그래서 **`search_text`에 다른 이름을 넣으면 검색 쿼리는 그대로 두고도 찾아진다.** 이 계획의 핵심이 이것이다.

## 2. 아티스트 다른 이름(별칭) — 1단계, 핵심

### 2.1 어디서 가져오나 (2026-11-08 실제 조회로 확인)

| 출처 | `Mariah Carey` 조회 결과 | 특징 |
|---|---|---|
| **MusicBrainz** (공개 API) | `머라이어 캐리`(ko_KR), `マライア・キャリー`(ja), `Mariah Carrey`… | 무료, 키 없음. 언어 표시가 있는 별칭. **초당 1회 제한, User-Agent 필수** |
| **Wikidata** | 한국어 이름 `머라이어 캐리` + 별칭 `머라이어 케리`, `머라이어캐리` | 무료. 외래어 표기 변형이 잘 들어 있음 |
| **멜론** 아티스트 검색 | `Mariah Carey` (한글 이름 없음) | 검색 목록에 다른 이름이 나오지 않아 **쓰지 않음** (구현 때 확인) |
| **벅스** 아티스트 검색 | `Mariah Carey(머라이어 캐리)` | 멜론과 같은 형식. 서로 확인용 |

반대 방향도 같은 출처로 해결된다. "아이유"로 저장된 가수는 MusicBrainz와 멜론에서 `IU`를 얻는다.

### 2.2 잘못 붙지 않게 (동명이인·오인 방지)

- 우리 라이브러리의 이름과 **정확히 같은 이름**(정규화 후)의 항목만 받는다. 비슷한 이름은 받지 않는다.
- MusicBrainz 검색 점수가 높고(≥ 95), 같은 이름의 후보가 여럿이면 우리 곡 제목과 겹치는 쪽을 고른다. 고를 수 없으면 받지 않는다.
- 멜론·벅스는 `영문(한글)` 짝이 우리 이름의 한쪽과 정확히 같을 때만 받는다.
- 받은 별칭은 출처를 함께 저장한다. 관리자가 직접 지운 별칭은 다시 가져오지 않는다.

### 2.3 저장과 색인

- `artists.aliases` (JSON): `[{"name": "머라이어 캐리", "source": "musicbrainz"|"wikidata"|"melon"|"bugs"|"manual"|"merged", "hidden": false}]`
- `artists.aliases_checked_at`: 마지막 조회 시각. 90일 지나면 다시 조회한다.
- 병합(merge.py)으로 합친 이름(`name_aliases`)도 별칭으로 색인한다 (`source: "merged"`).
- **아티스트 `search_text`**에 별칭을 넣는다. 그러면 아티스트 탭과 라이브러리 검색에서 찾아진다.
- **곡·앨범**은 별칭을 복사해 넣지 않고 **아티스트를 통해** 찾는다. 검색어의 각 단어가 곡(앨범) 자신의 글자에 없으면, 다른 이름이 있는 아티스트 중 그 단어가 맞는 아티스트의 곡(앨범)인지 본다. 그래서 "머라이어 캐리 hero"로 곡이 찾아지고, 별칭이 바뀌어도 곡 색인을 다시 만들 필요가 없다. (구현 때 바꾼 방식: 10만 곡에서 이전과 같은 응답 시간 확인 — 곡 검색 40ms, 결과 없음 7ms)
- 아티스트 색인은 스캔마다 다시 만들므로 `SEARCH_VERSION`은 그대로 둔다.
- 마이그레이션 1개 (컬럼 2개 추가).

### 2.4 언제 조회하나

- 스캔이 끝나면 백그라운드에서 조회한다. 앨범 설명·별점과 같은 스레드(`album_notes._lookup`)를 쓴다.
- 한 번에 최대 200명씩, MusicBrainz는 초당 1회를 지킨다. 아티스트 1,000명이면 첫 조회에 몇 번의 스캔이 걸린다.
- 관리자 화면에 "아티스트 다른 이름 찾기" 켬/끔과 "지금 모두 찾기" 버튼을 둔다(기존 '앨범 설명·별점 찾기' 옆).
- 서버가 인터넷에 못 나가면 조용히 건너뛴다. 검색은 기존대로 동작한다.

### 2.5 화면

- 아티스트 페이지: 이름 아래에 "다른 이름: 머라이어 캐리 · Mariah Carrey"를 작게 표시한다.
- 관리자: 아티스트 메뉴에 "다른 이름 편집"을 둔다. 직접 추가하거나, 잘못 붙은 것을 숨긴다(`manual`, `hidden`). 자동으로 못 찾은 가수는 이렇게 보완한다.
- 검색 결과: 별칭으로 찾았으면 "머라이어 캐리 → Mariah Carey"처럼 왜 나왔는지 보이게 한다.
- 검색어 추천(입력 중 제안)에도 별칭을 넣는다.

## 3. 표기 흔들림·오타·자판 실수 — 2단계

| 기능 | 방법 | 예 |
|---|---|---|
| **ㅐ/ㅔ 등 모음 접기** | 색인과 검색어 모두에서 외래어에 흔히 섞이는 모음을 하나로 접은 형태를 함께 넣는다(ㅐ→ㅔ, ㅒ→ㅖ). 원래 형태도 남겨 정확한 쪽이 앞에 온다 | "케리" = "캐리" |
| **한/영 자판 실수** | 검색어가 영문 자판 글자만으로 되어 있고 결과가 없으면 두벌식으로 바꿔 한 번 더 찾는다. 반대(한글로 친 영문)도 같다 | "dkdldb" → "아이유", "ㅑㅕ" → "iu" |
| **오타 허용 ("이것을 찾으셨나요?")** | 결과가 없거나 적을 때 pg_trgm `word_similarity`로 아티스트 이름·별칭·앨범 제목 중 가까운 것을 제안한다. 이미 있는 trigram 인덱스를 쓴다 | "머라이어 캐라" → "머라이어 캐리를 찾으셨나요?" |
| **입력 중 글자** | 제안에서 마지막 글자가 조합 중이면("머라이ㅇ") 그 글자의 초성까지 맞는 것을 찾는다 | "머라이ㅇ" → 머라이어 캐리 |

오타 허용은 결과가 없을 때만 제안으로 보여 준다. 일반 결과에 섞으면 엉뚱한 결과가 늘어서다.

## 4. 결과 순서 — 2단계

곡·앨범·아티스트 각각 다음 순서로 정렬한다.
1. 이름(또는 별칭)이 검색어와 정확히 같음
2. 이름이 검색어로 시작함
3. 이름에 들어 있음
4. 다른 필드(곡의 아티스트, 앨범명)로 찾아짐

같은 단계 안에서는 재생 횟수가 많은 쪽을 앞에 둔다(기존 `play_counts`). 지금 곡 검색의 `relevance` 정렬을 이 규칙으로 바꾸고, 앨범·아티스트에도 적용한다.

## 5. 곡·앨범 제목의 다른 언어 — 3단계 (선택)

- 예: `Love wins all` ↔ "러브 윈즈 올", `Dynamite` ↔ "다이너마이트".
- 곡 단위 조회는 양이 많아서(수만 곡) 아티스트만큼 쉽지 않다. 멜론 곡 정보에 한글 독음이 없는 경우도 많다.
- 1·2단계를 써 보고 필요하면 한다. 그때는 **자주 듣는 곡**(재생 기록 상위)부터 조회하는 방식을 검토한다.

## 7. 확인 방법

- **검색어 시험 목록**을 만들어 각 단계 전후로 돌린다. 개발 DB에 해외·국내 가수 표본을 추가한다.
  - 머라이어 캐리 / 머라이어 케리 / 머라이어캐리 / Mariah Carey / mariah
  - 아이유 / IU / ㅇㅇㅇ / dkdldb
  - 비틀즈 / 비틀스 / The Beatles / beatles
  - 방탄소년단 / BTS / 머라이어 캐라(오타)
- 별칭 조회는 실제 사이트에 연결해 표본 50명으로 정확도를 본다. 잘못 붙은 것이 있으면 2.2의 규칙을 조인다.
- 성능: 10만 곡 벤치(scripts/bench)로 색인 재생성 시간과 검색 응답 시간을 이전과 비교한다. `search_text` 길이 상한(4000자)도 넘지 않는지 확인한다.
- 스모크 테스트와 업그레이드 테스트(이전 DB에서 새 이미지 시작)는 매 릴리즈 하던 대로 한다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 동명이인에 별칭이 잘못 붙음 | 정확히 같은 이름만, 점수 기준, 곡 제목 교차 확인. 관리자 숨김 |
| 외부 사이트 구조 변경·차단 | 출처 4곳 중 하나만 돼도 됨. 실패는 기록만 하고 건너뜀 |
| MusicBrainz 요청 제한 | 초당 1회, User-Agent, 90일 재조회 |
| 색인이 커져 느려짐 | 별칭 수 상한(아티스트당 8개), 벤치로 확인 |
| 인터넷이 안 되는 NAS | 조회만 꺼지고 수동 별칭·자판 실수·모음 접기는 그대로 동작 |
